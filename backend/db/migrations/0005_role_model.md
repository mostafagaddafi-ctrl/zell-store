# نموذج الأدوار: `postgres` اليوم ← `zell_definer` / `zell_order` غداً

وثيقة توضيحية مصاحبة لمسودة `0005`. **مفيش حاجة من ده منفّذة.**

---

## ١) الوضع الحالي

| مين | الدور | بيعمل إيه |
| --- | --- | --- |
| مورد Retool `SUPABASE` | `postgres` (login, BYPASSRLS) | كل استعلامات الباك إند |
| Supabase REST | `anon` / `authenticated` | **مقفولين** بعد 0002 |
| أدوات Supabase | `service_role` | Storage لاحقاً، من الباك إند فقط |

`postgres` دلوقتي بيعمل كل حاجة: قراءة المنتجات، إنشاء الطلبات، إدارة اللوحة.
ده مقبول **مؤقتاً** لأن التطبيق مقفول على أعضاء الـ org، لكنه مش مقبول بعد الفتح العام.

---

## ٢) الأدوار المقترحة

```
zell_definer   NOLOGIN, NOBYPASSRLS   ← مالك دالة create_order (SECURITY DEFINER)
                                        صلاحياته: SELECT على products/settings،
                                        INSERT على orders/order_items، وبس.
                                        مفيش UPDATE/DELETE خالص.

zell_order     LOGIN                  ← دور الويب سيرفر العام (مستقبلاً)
                                        صلاحيته الوحيدة: EXECUTE على create_order.
                                        مفيش SELECT ولا INSERT على أي جدول.

zell_read      LOGIN                  ← قراءة المنتجات النشطة + public_settings (لاحقاً)

postgres       LOGIN, BYPASSRLS       ← Retool والباك إند واللوحة والـ migrations
service_role   NOLOGIN, BYPASSRLS     ← Storage من الباك إند فقط
```

**ليه المالك NOLOGIN ومن غير BYPASSRLS؟**
`SECURITY DEFINER` معناها إن الدالة بتشتغل بصلاحيات مالكها. لو المالك `postgres`،
فأي ثغرة منطق جوه الدالة بتتحوّل لصلاحيات شبه كاملة على الداتابيز.
مع `zell_definer` أسوأ حالة = INSERT في `orders`/`order_items` وقراءة منتجات —
مفيش وصول لباقي الجداول ولا تعديل ولا حذف. وكونه `NOLOGIN` يعني محدش يقدر
يتصل بيه مباشرة من بره.

**نتيجة مهمة**: لأن `zell_definer` مالوش `BYPASSRLS`، الـ RLS بيسري عليه فعلاً،
فلازم policies صريحة (موجودة في 0005) — وده الفرق الجوهري عن الاعتماد على `postgres`.

## ٣) إزاي `zell_order` يتعايش مع اتصال Retool الحالي (`postgres`)؟

الاتنين **مايتعارضوش** — كل واحد مسار منفصل لنفس الدالة:

```
                       ┌─────────────────────────────┐
Retool Backend ──────► │                             │
 (دور postgres)        │  public.create_order(...)   │──► تشتغل بصلاحيات
                       │  SECURITY DEFINER           │    zell_definer
Vercel/Next (لاحقاً) ──►│  owner = zell_definer       │
 (دور zell_order)      └─────────────────────────────┘
```

- الدالة **واحدة** ومنطق الطلب فيها مرة واحدة بس.
- `postgres` بياخد `GRANT EXECUTE` صريح في 0005 عشان الباك إند الحالي يقدر يناديها.
  (هو مش المالك بعد `alter function ... owner to zell_definer`، فالمنح لازم صريح.)
- `zell_order` بياخد `GRANT EXECUTE` وقت الفتح العام بس.
- مين بيشتغل بأي صلاحية داخلياً؟ **الاتنين بصلاحيات `zell_definer`** وقت تنفيذ الدالة.

### ⚠ تصحيح أمني مهم — حدود حماية `zell_definer`

المكسب من `zell_definer` هو **تقليل أثر ثغرة منطقية جوّا الدالة نفسها** (SQL injection
داخلي، أو خطأ منطق، أو استغلال search_path) — وبس.

**هو مش حماية من تسريب اتصال `postgres` نفسه.** لو بيانات اتصال مورد Retool
اتسرّبت، المهاجم بيبقى دور `postgres` بالكامل: `BYPASSRLS`، مالك كل الجداول،
ويقدر يقرا ويعدل ويمسح أي حاجة، ويعمل `alter function` أو `set role zell_definer`
أو يلغي أي policy — يعني **اختراق كامل للداتابيز**.

الحماية من السيناريو ده ملهاش علاقة بالدالة، وبتتم بحاجات تانية:

1. **إن المورد مايستخدمش `postgres` أصلاً** — دور `zell_app` محدود بـ SELECT/INSERT/UPDATE
   على اللي اللوحة محتاجاه فقط، من غير DDL ولا `BYPASSRLS` ولا ملكية جداول.
   **دي أهم خطوة المتبقية.**
2. تدوير كلمة سر `postgres` وحصر استخدامها في الـ migrations اليدوية.
3. تقييد الشبكة (IP allowlist / Supabase connection pooler) وتفعيل تدقيق الدخول.
4. نسخ احتياطي دورية (Supabase PITR) كخطة تعافي.

### خطة التحويل (٣ مراحل، بدون توقف)

| المرحلة | الباك إند | الحالة |
| --- | --- | --- |
| الآن | `createOrderSql.ts` (نفس المنطق من التطبيق) | شغّال |
| بعد تنفيذ 0005 | نفس الكود + اختبار الدالة بالتوازي (shadow) والمقارنة | تحقق |
| بعد التأكد | `select public.create_order(...)` من الباك إند، وحذف الـ SQL من التطبيق | نهائي |

في المرحلة الأخيرة يُفضّل كمان استبدال اتصال Retool من `postgres` لدور
`zell_app` محدود (SELECT/INSERT/UPDATE على ما تحتاجه اللوحة فقط) —
وده تغيير في إعداد المورد، مش في الكود.

## ٤) البصمة (fingerprint) — مين بيحسبها

```
المتصفح ──(طلب عادي، مفيش بصمة)──► الباك إند الموثوق
                                     │
                                     ├─ ياخد IP من هيدر البروكسي + User-Agent
                                     ├─ fingerprint = HMAC-SHA256(secret, ip|ua)
                                     │  (secret في مورد Retool / متغيّر بيئة)
                                     └─► create_order(..., p_fingerprint => hmac, ...)
```

- **ممنوع** إن المتصفح يبعت البصمة أو الـ IP — أي قيمة جاية منه تتجاهل تماماً.
- الداتابيز بتخزّن الـ HMAC فقط، مفيش IP خام (أفضل للخصوصية وللالتزام القانوني).
- تغيير الـ secret بيبطّل كل البصمات القديمة — مقبول، الجدول مؤقت بطبيعته.

## ٥) idempotency — ليه بالقيد الفريد وبربط request hash

- المفتاح بيتولد في **الباك إند** لكل محاولة إرسال (UUID v4)، ويتبعت مع الطلب.
- الذرّية من `unique index` + `on conflict do nothing` — مفيش سباق بين
  `select` و`insert` زي ما كان في المسودة الأولى.
- مع المفتاح بنخزّن `request_hash` = SHA-256 لمحتوى الطلب (الأصناف والاسم والتليفون
  والمحافظة والعنوان والملاحظات).
  - نفس المفتاح + نفس الهاش → **replay**: ترجع نفس الطلب، من غير إنشاء جديد.
  - نفس المفتاح + هاش مختلف → **رفض** بكود `ZELL_IDEMPOTENCY_MISMATCH` (45003)،
    عشان محدش يعيد استخدام مفتاح قديم لتمرير طلب مختلف.
