# المعمارية

الوثيقة دي بتشرح **الحدود** و**تدفق البيانات** و**القواعد اللي ممنوع
تتكسر** — ومكان تطبيق كل قاعدة.

الوثيقة دي بتوصف حالة النظام الحيّ وقت آخر تحديث ليها. لمعرفة النسخة
بالظبط، راجع تاريخ Git للملف ده.

---

## ١) التطبيقات وحدودها

    apps/storefront   →  للزباين. قراءة فقط. مفيش كتابة خالص.
    apps/admin        →  للأدمن. قراءة وكتابة. محمي بـ Supabase Auth.
    packages/core     →  منطق صافي. مفيش I/O ولا أسرار ولا شبكة.

### قواعد الحدود

| القاعدة | السبب |
| --- | --- |
| المتجر **مابيكتبش** في الداتابيز | كل الكتابة من اللوحة أو من دالة إنشاء الطلب (لسه ما اتعملتش) |
| اللوحة **مابتستوردش** من المتجر والعكس | التطبيقين بيتنشروا لوحدهم؛ أي استيراد متقاطع بيربط نشرتين ببعض |
| `packages/core` **مفيهوش** `fetch` ولا `process.env` | بيتحمّل في المتصفح والسيرفر؛ أي I/O جواه بيسرّب أو بيكسر |
| الاتنين بيستوردوا `@zell/core` | نقطة واحدة للتسعير والأنواع — نسختين معناها سعرين |

### ⚠️ `backend/` و `frontend/`

نسخة Retool القديمة، **مرجع تاريخي**. مفيش حاجة في `apps/` بتستوردهم،
ومفيش حاجة فيهم بتتنفّذ. فيهم منطق تسعير قديم — **المرجع المعتمد هو
`packages/core/src/pricing.ts` وبس**.

## ٢) تدفق البيانات

### قراءة المتجر

    صفحة (Server Component)
      → lib/data/source.ts        ← STOREFRONT_DATA_SOURCE يحدد المصدر
          fallback  → lib/catalog.ts        (CI والتطوير المحلي)
          supabase  → lib/data/queries.ts   (Production)
      → PostgREST بمفتاح قراءة
      → mappers.ts → @zell/core types
      → كاش ٣٠٠ ثانية

**مفيش fallback ضمني.** متغير ناقص أو قيمة غير معروفة = استثناء صريح.
السبب: متجر شغّال بأسعار قديمة أخطر بكتير من بناء فاشل.

### قراءة اللوحة

    صفحة محمية
      → requireAdminPage()        ← getUser() + admin_users
      → lib/adminData.ts → lib/data/reads.ts
      → PostgREST بصلاحية الخدمة
      → rows.ts → أنواع اللوحة

مفيش كاش خالص: اللوحة بتعرض حالة تشغيل لحظية، وأي كاش بيضلّل.

### كتابة اللوحة

    Server Action
      ١. requireAdminAction()   → UNAUTHENTICATED | FORBIDDEN
      ٢. guardMutations()       → DISABLED
      ٣. تحقق المدخلات           → VALIDATION
      ٤. تزامن تفاؤلي            → CONFLICT | NOT_FOUND
      ٥. الكتابة (PATCH أو دالة ذرّية)

**الترتيب ملزم.** الصلاحية قبل علم الجاهزية — العكس بيقول لمجهول إن
"التعديلات موقوفة"، وده تسريب معلومة عن حالة النظام.

## ٣) القواعد الثابتة وأماكن تطبيقها

| القاعدة | مكان التطبيق |
| --- | --- |
| الفلوس بالقرش والأطوال بالسنتيمتر — integer | أعمدة الداتابيز + `@zell/core` |
| السعر المعروض بيتحسب في الواجهة من قواعد الداتابيز | `@zell/core` |
| معرّفات الصور **نصوص** | `rows.ts` (`String(row.id)`) → `AdminImage.id` → الـ RPC |
| تزامن تفاؤلي بدقة الميلي ثانية | `lib/mutations/concurrency.ts` |
| الكتابة على أكتر من صف = دالة ذرّية | `zell_*` (٧ دوال) |
| مفيش `NEXT_PUBLIC_` | `lib/auth/env.ts` + `lib/data/client.ts` |
| `server-only` على كل ملف فيه مفاتيح | `lib/data/*` · `lib/auth/*` · `lib/mutations/*` · `lib/validation/*` |
| أخطاء Supabase مابتخرجش للعميل | `lib/mutations/errors.ts` + طبقة النقل |
| ممنوع القص الصامت | `pricing.ts` (`requiredLength` بترجّع فشل صريح) |
| المنتج الجديد مخفي إجباريًا | `lib/validation/product.ts` |
| المنتج النشط لازم يكون مكتمل | `lib/mutations/products.ts` — **تطبيق بالكود بس** |

### ⚠️ قاعدة واحدة مطبّقة بالكود مش بالداتابيز

شرط **جاهزية التفعيل** (وصف + فايدة مختصرة + صورة رئيسية) مفيش قيد في
الداتابيز بيفرضه. يعني:

- أي مسار كتابة جديد على `products` لازم يمر على `activationReadiness`
- الكتابة المباشرة بـ SQL أو من لوحة Supabase **بتتخطى القاعدة بالكامل**

لو القاعدة دي بقت حرجة، مكانها الصح قيد أو trigger.

## ٤) التزامن التفاؤلي — خمس خطوات

    ١. اقرا updated_at الحالي من الداتابيز
    ٢. مفيش صف                       ->  NOT_FOUND
    ٣. قارنه بالمتوقع بدقة الميلي     ->  CONFLICT
    ٤. PATCH بفلتر updated_at = القيمة اللي السيرفر قراها
    ٥. صفر صفوف متأثرة               ->  CONFLICT

الخطوة ٣ لوحدها **مش ذرّية**. الخطوة ٤ لوحدها **مش دقيقة** — Postgres
بيخزّن ميكروثانية وJavaScript بيقرا ميلي، فالمقارنة النصية بتدي تعارض
وهمي لأي طابع عدّى على الواجهة ورجع.

**مفيش trigger على `updated_at` في أي جدول** — فكل `PATCH` بيبعتها صراحة.
من غير كده الطابع مابيتغيرش والتزامن التفاؤلي بيبقى بلا معنى.

## ٥) الذرّية: إيه اللي محتاج دالة داتابيز

PostgREST مابيعملش معاملات بين طلبات. فأي عملية بتلمس أكتر من صف أو
أكتر من مفتاح **لازم** تكون دالة.

| العملية | الدالة |
| --- | --- |
| محتوى المتجر (٦ مفاتيح) | `zell_save_content` |
| الشحن (٤ مفاتيح) | `zell_save_shipping` |
| الهوية (٤ مفاتيح) | `zell_save_identity` |
| ترتيب المنتجات | `zell_reorder_products` |
| ترتيب صور المعرض | `zell_reorder_product_images` |
| الصورة الرئيسية | `zell_set_primary_product_image` |

### ليه `GET` ثم `UPSERT` مش كفاية

العملية الجماعية **ذرّية كـكتابة**، لكن فحص النسخة مش جواها:

    ١. GET أحدث updated_at
    ٢. قارن بالمتوقع
    ٣. UPSERT

بين ٢ و ٣ يقدر أدمن تاني يحفظ، وحفظه يتمسح **من غير أي تعارض يظهر**.
الفحص لازم يكون جوه نفس المعاملة.

### طابع نسخة الهوية — نقطة دقيقة

`zell_save_identity` بتقفل **أربعة** مفاتيح؛ `logo_url` **مش** فيهم.
فطبقة القراءة بتحسب `StoreIdentity.updatedAt` على نفس الأربعة
(`IDENTITY_SAVE_KEYS`). لو كان محسوب على اللوجو كمان، أي تغيير للوجو
كان هيخلي كل حفظ هوية يرجّع `CONFLICT` وهمي.

## ٦) المفاتيح وحدودها

| المفتاح | بيعمل إيه |
| --- | --- |
| `SUPABASE_ANON_KEY` | الهوية بس: دخول · تجديد · خروج |
| `SUPABASE_SERVICE_ROLE_KEY` | كل قراءات وكتابات اللوحة |
| `SUPABASE_READ_KEY` | قراءة المتجر |

⚠️ `service_role` **بيتخطى RLS بالكامل** وهو **حل انتقالي**. لازم يتبدل
بدور محدود الصلاحية. لحد ساعتها، الحد الوحيد على اللوحة هو كود التطبيق
نفسه — وده السبب إن `requireAdminAction()` مكررة في كل Action.

## ٧) الصور

الداتابيز بتخزّن `bucket` + `object_path`، **مش** الرابط الكامل. الرابط
بيتركّب في `packages/core/src/imageUrl.ts` — فتغيير المشروع أو إضافة CDN
تعديل في مكان واحد.

| | |
| --- | --- |
| الرفع | `POST /api/admin/products/[productId]/images` |
| النوع | من **البايتات** — اسم الملف وMIME من المتصفح بيتجاهلوا |
| المسار | `products/{id}/{uuid}.{ext}` — بيتبنى في السيرفر |
| الأبعاد | هيدر بس (`image-size`) — **مفيش فك ضغط للبكسلات** |
| التكرار | `checksum` SHA-256 + فهرس فريد لكل منتج |
| الرئيسية | `zell_set_primary_product_image` بأقفال `FOR UPDATE` |

⚠️ **ترتيب العرض في اللوحة `sortOrder` تصاعدي**، مش الرئيسية الأول.
طبقة القراءة بترتب `is_primary.desc` للمتجر — لو أسهم الترتيب في اللوحة
اشتغلت على ترتيب العرض ده، كل إعادة ترتيب كانت هتثبّت الرئيسية في
`sort_order = 0`: قاعدة عرض بتكتب في البيانات.
