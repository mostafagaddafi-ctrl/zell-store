# المرحلة ١ — فصل المتجر عن الداشبورد (الهيكل فقط)

الفرع: `feat/storefront-admin-split`

## اللي اتعمل

| # | البند | الحالة |
| --- | --- | --- |
| 1 | تحويل الريبو إلى pnpm workspace | ✅ |
| 2 | `apps/storefront` — تطبيق Next.js 15 مستقل لـ Vercel | ✅ |
| 3 | `packages/core` — **نسخة مرجعية جديدة** للأنواع والتسعير والتحقق | ⚠️ مش توحيد كامل — اقرا القسم اللي تحت |

## اللي **ما** اتعملش (بقرار صريح)

- مفيش اتصال بقاعدة البيانات من `apps/storefront`.
- مفيش إنشاء طلب — زرار التأكيد معطّل، ومفيش أي مسار بديل لإرسال الطلب من صفحة الـ checkout.
- مفيش ربط لـ Supabase Storage ولا صور.
- مفيش SQL ولا migrations.
- مفيش أسرار ولا ملفات `.env` في الريبو.

## ⚠️ منطق التسعير — النسخ لسه أربعة، مش واحدة

الادعاء إن التسعير «اتوحّد» **غلط**. اللي حصل إننا ضفنا نسخة مرجعية جديدة،
والنسخ القديمة كلها لسه موجودة وشغّالة في الإنتاج:

| # | المكان | الحالة | بيخدم مين |
| --- | --- | --- | --- |
| 1 | `packages/core/src/pricing.ts` | 🆕 المرجع الجديد | متجر Next.js فقط |
| 2 | `backend/lib/pricing.ts` | 🔴 شغّالة في الإنتاج | دوال Retool |
| 3 | `frontend/lib/core/pricing.ts` | 🔴 شغّالة في الإنتاج | داشبورد Retool |
| 4 | داخل `backend/lib/createOrderSql.ts` | 🔴 شغّالة في الإنتاج | **الحساب المعتمد** في الداتابيز |

> نسختي Retool (2) و(3) كانوا **اتفرّقوا فعلاً** عن بعض قبل المرحلة دي
> (4646 بايت مقابل 4869 بايت). والنسخة (4) هي الوحيدة اللي بيتحصّل بيها فلوس.

### قاعدة مؤقتة ملزمة

طول ما النسخ موجودة: **أي تعديل في منطق التسعير يتكتب في `packages/core` الأول،
وبعدين يتنسخ يدوياً للنسختين القديمتين في نفس الـ PR، مع ذكر ده في وصف الـ commit.**
أي نسخة SQL تتعدّل عن طريق migration مراجَعة بس.

### خطة الانتقال التدريجي

| مرحلة | الخطوة | شرط الانتقال للي بعدها |
| --- | --- | --- |
| أ | متجر Next.js يستهلك `@zell/core` (اتعمل) | البناء ينجح |
| ب | دوال Retool في `backend/` تستورد من `@zell/core` بدل `backend/lib/pricing.ts` | اختبار الطلبات على staging |
| ج | داشبورد Retool يستورد من `@zell/core` بدل `frontend/lib/core/pricing.ts` | مراجعة بصرية للوحة |
| د | حذف النسختين (2) و(3) | كل ما فوق أخضر |
| هـ | مطابقة نسخة SQL (4) مع `@zell/core` بـ migration | مراجعة + staging |

**ممنوع حذف أي نسخة قديمة قبل الوصول للمرحلة (د).**

## تصحيحات بعد المراجعة الأولى

| # | المشكلة | التصحيح |
| --- | --- | --- |
| 1 | `requiredLengthCm` كانت بتعمل `Math.min(..., max_length_cm)` فبتقصّ المقاس الكبير **بصمت** — الزبون ياخد طول أقل من اللي محتاجه | اتشالت واتبدلت بـ `requiredLength()` بترجّع نتيجة صريحة `{ ok: false, code: 'exceeds_max' }` والواجهة بتعرض «المقاس أكبر من الحد المتاح» وبتمنع الإضافة للسلة |
| 2 | `step_cm = 0` بيعمل modulo على صفر في `validateLength`، و`lengthOptions` بتدخل loop لا نهائي | `validateRules()` جديدة بتتحقق من `width_cm`/`step_cm`/`min`/`max`/السعر، وكل دالة بتعدّي منها. `lengthOptions` بترجّع `[]` لو القواعد غلط وليها سقف ٢٠٠ خيار |
| 3 | مقاسات شباك خيالية | حد أقصى ٥٠٠٠ سم للعرض والارتفاع برسالة واضحة |
| 4 | `catalog.ts` ممكن يتفهم كمصدر بيانات | الصادرات اتسمّت `getFallbackProducts` / `getFallbackSettings` عشان مكان الاستدعاء نفسه يفضح إنها مؤقتة، مع بانر تحذير في أول الملف |
| 5 | رابط واتساب في الـ checkout ممكن يتفهم كإنشاء طلب | اتشال من الـ checkout تماماً. واتساب بقى للاستفسار بس ومكانه الصفحة الرئيسية |
| 6 | ادعاء «التسعير بقى نسخة واحدة» | اتصحح، والقسم اللي فوق بيوثّق الأربع نسخ وخطة الانتقال |

## الهيكل

```
zell-store/
├─ apps/storefront/        Next.js (App Router) → Vercel
│   ├─ app/                / · /product/[id] · /cart · /checkout
│   ├─ components/store/   مكوّنات المتجر
│   ├─ components/ui/      Button · Field
│   └─ lib/                cart (localStorage) · catalog (FALLBACK مؤقت) · cn
├─ packages/core/          تسعير · أنواع · تحقق · رقم الطلب · روابط الصور
├─ backend/                تطبيق Retool — من غير أي تعديل
└─ frontend/               تطبيق Retool — من غير أي تعديل
```

## التشغيل محلياً

```bash
pnpm install

pnpm build
```

> أول `pnpm install` هيولّد `pnpm-lock.yaml` — اعمله commit عشان البناء يبقى ثابت.

## متغيّرات البيئة (مرحلة ٢ — مش دلوقتي)

الأسماء بس للتوثيق، من غير أي قيم، وتتحط في لوحة Vercel مباشرة:

- `NEXT_PUBLIC_SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` — server-only، للـ API route بس
- `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`

## المرحلة الجاية

1. قراءة المنتجات والإعدادات من Supabase (server-side، `anon` + policies محدودة).
2. `/api/orders`: validation + rate limiting + idempotency ← عملية ذرّية في الداتابيز.
3. ربط الصور من `product_images` و `site_images`.
4. صفحة نجاح `/order/[orderNumber]`.
