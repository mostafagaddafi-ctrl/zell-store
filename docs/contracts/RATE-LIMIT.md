### ١-٢ من Vercel (منقول، قراية بس، 2026-11-06)
- الخطة **Hobby**، والمشروعين على نفس الفريق. Custom Rules: 3 لكل مشروع. Rate Limit: قاعدة واحدة لكل مشروع من ضمن الـ 3 ([الوثيقة](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules)).
  - **اختلاف مصادر (مش محسوم):** المعلومة المنقولة من الوثائق = قاعدة Rate Limit **واحدة** لكل مشروع. والجرد المنقول من الواجهة (§٣-٤، 22:09–22:17Z) بيعرض `Rate Limit 0/3`. الاختلاف ده **مش محسوم، ومابيثبتش** إن مسموح بتلات قواعد Rate Limit. **ومابيأثّرش على التصميم المقبول**، اللي بيضيف قاعدة واحدة بس لكل مشروع.
- Fixed Window من 10 ثواني لـ 10 دقايق، والعدّ بالـ IP أو JA4، و**كل منطقة ليها عدّاد منفصل** ([الوثيقة](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)). أول 1,000,000 طلب مسموح في الشهر مشمولين ([الإعلان](https://vercel.com/changelog/rate-limiting-now-available-on-hobby-with-higher-included-usage-on-pro)). **بعد المليون على Hobby: مش معروف.**
- إعدادات Firewall: `404 Config not found` في المشروعين. **سبب للتحقق في §٣-١، مش إذن باستبدال الإعداد.**
- Node.js 24.x. شرط Hobby بالنص: «the Hobby plan restricts users to non-commercial, personal use only» ([الوثيقة](https://vercel.com/docs/plans/hobby)). **مش محسوم، وإخراجه من العقد مش إثبات إن الخطة مناسبة** (§٦).

## ٢) التصميم — مابيعتمدش على مسار الصفحة
| | المتجر (`zell-store`) | اللوحة (`admin`) — **اتلغت: قرار المالك (ب) 2026-11-07 (§٧-٥)** |
| --- | --- | --- |
| الاسم | `zell-rl-storefront-post` | `zell-rl-admin-post` |
| الشرط | `Method = POST` **و** `Path` **مش** `/api/revalidate` **ومش** `/api/health` | `Method = POST` (أي مسار) |
| يغطّي | الأوردر + الكوبون + **أي** نداء Server Action (التتبّع) على أي مسار وبأي شكل (header أو multipart) | الدخول + كل Server Actions الإدارة + الخروج، على أي مسار |
| العدّ | IP | IP |
| الفترة | 60 ثانية (Fixed Window) | 60 ثانية (Fixed Window) |
| السقف (اقتراح، §٧-١) | **20** | **60** |
| لو عدّى | **429 Too Many Requests** لباقي الفترة | **429 Too Many Requests** لباقي الفترة |

- **ليه «كل POST» مش مسارات:** في المتجر، الـ POST من المتصفح هي التلاتة بس (§١-١)، فـ «كل POST ما عدا اللي سيرفر لسيرفر» بيغطّي التتبّع مهما كان المسار أو الشكل اللي اتبعت بيه الـ Action. و`/api/revalidate` و`/api/health` برّه لأنهم بييجوا من سيرفرات Vercel، وممكن يعدّوا السقف وقت تعديلات كتير.
- **اللوحة (قرار المالك):** «كل POST» بيغطّي الدخول على أي مسار، **بس بيحد كمان عمليات الإدارة**. السقف 60 في الدقيقة واسع لاستخدام إنسان، بس رفع صور كتير مرة واحدة ممكن يقرّب منه، ولو عدّى المالك بيتمنع لحد ما الدقيقة تخلص. **البديل (ب):** مفيش قاعدة للوحة دلوقتي (الحد على الدخول بيبقى على باسورد قوي، وحماية Supabase Auth اللي مش متحقق منها هنا). **البديل (ج)** (قاعدة على `/login` بس) **مرفوض** لأنه مابيغطّيش الـ Action على مسار تاني (§١-١).
- **الإعدادات دي مش في الريبو** (Vercel بس)، فالقاعدة بالحرف هنا وفي الذاكرة، وأي تغيير بعدين = قرار جديد.

## ٣) التنفيذ — في Vercel، كل خطوة بأمر المالك لوحدها
- **مين:** الشات المربوط بـ Vercel (أو المالك من الشاشة)، **بالقيم في §٢ بالحرف**. ممنوع أي تغيير تاني (لا Managed Rulesets، ولا Bot Protection، ولا Attack Challenge Mode، ولا قواعد تانية). **الاستثناء الوحيد:** إعدادات CRS الظاهرة في مسودة `zell-store` الأولى، بقيم مرجع §٣-٤ بالحرف، ولمرة النشر دي بس. ده مش تعديل متعمّد على CRS، ومايتعمّمش على أي مشروع أو نشر تاني.
- **٣-١ قبل الإضافة (قراية بس):** لكل مشروع:
  - اسم المشروع، و**الإعداد الكامل الحالي وإصداره** (version أو ما يقابله) لو متاح. ولو `Config not found`: يتسجّل كده بالظبط.
  - تأكيد إن **429** متاح بالاسم كإجراء لـ Rate Limit على Hobby، وإن الشرط ينفع يتكتب زي §٢: `Method = POST` + **نفي** المسارين (للمتجر).
  - إن الإضافة بتتعمل **كإضافة قاعدة** (مش PUT لإعداد كامل). لو الـ API ماعندهوش غير استبدال الإعداد كله: **وقف وتبليغ**.
  - **وقف وتبليغ** لو: فيه قواعد موجودة، أو 429 مش متاح، أو النفي مش متاح، أو الإضافة محتاجة استبدال الإعداد.
- **٣-٢ المتجر:** إضافة `zell-rl-storefront-post` بس ← قراية الإعداد كله ← **مقارنة بالإعداد قبل**: الفرق الوحيد = القاعدة دي. ويتسجّل **Rule ID** والإصدار الجديد. **لمسودة `zell-store` الأولى:** قراية active قبل النشر مش ممكنة (`Config not found`)، فالمقارنة بتبقى حسب §٣-٤: المسودة قبل الـ Publish = المرجع، وactive بعد الـ Publish = نفس المرجع.
- **٣-٣ اللوحة (لو المالك اختار (أ)):** نفس الخطوات على `zell-rl-admin-post`، بأمر لوحده.
- **اللي بيتسجّل:** المشروع، وRule ID، والإصدار قبل/بعد (لو متاح)، والشرط، والفترة، والسقف، والإجراء، والحالة، ووقت التطبيق، ومصدر كل ده (شاشة أو API). **من غير** رابط اللوحة، ولا توكنات، ولا IPs.

## ٤) التحقق
- **٤-١ مقارنة الإعداد** (§٣-٢/٣-٣): مطابق لـ §٢، والفرق محصور في القاعدة. وإلا وقف. **لمسودة `zell-store` الأولى (§٣-٤):** المسودة قبل الـ Publish بتطابق المرجع، وactive بعد الـ Publish بتطابق نفس المرجع (قيم السلوك)، لأن قراية active قبل النشر مش ممكنة.
- **٤-٢ تجربة المالك (استخدام عادي، مش اختبار حد):** في المتجر: كوبون مرة وتتبّع مرة. وفي اللوحة: دخول مرة، وفتح طلب. **من غير أوردر.** الكل يشتغل زي النهارده.
