### ٣-٤ مفاتيح المسار والـ 404
- أي `/product/<قيمة>` بيتولّد ويتكاش لوحده، ومنه قيم مختلفة لنفس المنتج (زي `1` و`01` لأن `Number('01') = 1`) وقيم مش منتجات (404). كلها بتمر على fetch عليه التاج (من الـ layout على الأقل)، فالإبطال بيشملها؛ والاختبار بيثبت ده لـ 404 → 200. **عدد مفاتيح الكاش بيكبر مع عدد القيم المختلفة اللي بتتطلب**؛ ده أثر معلن، ومفيش سياسة معرفات ولا تحويلات جديدة في العقد ده.
- الـ 404 بيفضل لحد إبطال ناجح أو تجديد زمني ناجح، **من غير وعد انتهاء صارم بعد 300 ثانية**. **مقبول بقرار المالك 2026-11-15 (§٦ بند ٣)، بشرط نجاح T4** (إثبات الإبطال والانتقال من 404 لـ 200).

## ٤) القبول في CI (من غير Production) — اختبار التكامل (§٢-٢) لازم ينجح كله
كل حالة بتفشل صراحة لو الدليل مش موجود (مفيش تخطّي صامت):
- **T1 أول طلب وإعادة الاستخدام:** `GET /product/<id>` → 200 فيه السعر الصناعي (أ). طلب تاني → نفس الـ HTML، **ومفيش طلبات جديدة للمصدر الصناعي** (العدّاد)، وهيدر كاش Next = HIT.
- **T2 المدة:** هيدر `Cache-Control` على صفحة المنتج مش `private` ولا `no-store`، وفيه `s-maxage=300` بالظبط (ده دليل المدة من السيرفر، مش من المانيفست).
- **T3 تغيير السعر + الإبطال الحقيقي:** تغيير السعر في المصدر الصناعي لـ (ب) → طلب → لسه (أ) (كاش). `POST /api/revalidate` بمفتاح الاختبار → 200 و`ok: true` → **أول** طلب بعدها: الـ HTML والعنوان ووصف الميتاداتا (سطر السعر) وOG كلهم بـ (ب). ونفس الإندبوينت بمفتاح غلط → 401 ومفيش تغيير.
- **T4 الـ 404 والإضافة والإخفاء:** `/product/<id جديد>` → 404. إضافة المنتج في المصدر + إبطال → 200 بالسعر. تحويله لـ `is_active = false` (المصدر بيحترم فلتر `is_active=eq.true` زي PostgREST) + إبطال → 404 (منطق الكود الحالي في `getStorefrontProductById`).

### ٧-٣ التغيير المقترح (PR تنفيذ واحد)
- **«ملف اتلمس»** = أي مسار ظهر في الفرق: **إضافة · تعديل · حذف · تغيير نوع · وطرفي أي نقل أو إعادة تسمية (المسار القديم والمسار الجديد الاتنين)**. لو أي واحد منهم جوه §٧-٢ → التشغيل.
- **طريقة جمع الفرق:** السكربت نفسه هو اللي بيجمع الفرق (مش الـ workflow)، بـ `git -c core.quotepath=false diff --no-renames --name-only -z <range>`:
  - `--no-renames` بيقفل كشف إعادة التسمية، فالنقل بيطلع **حذف للمسار القديم + إضافة للمسار الجديد**، والاتنين في القايمة.
  - `-z` بيفصل المسارات بـ NUL، فالمسارات اللي فيها مسافات أو حروف خاصة بتتقري زي ما هي من غير اقتباس.
  - الـ range: `pull_request` = `<base.sha>...HEAD` (من نقطة التفرّع)، والـ checkout بـ `fetch-depth: 0` زي jobs الـ SQL.
- سكربت جديد `scripts/isr-integration-scope.mjs` بيطبع `run=true|false` والملفات اللي طابقت:
  - `workflow_dispatch` → `true`.
  - **push لـ main → `true` دايمًا** (التغطية الكاملة بعد كل دمج؛ المراجع قبله، §٧-٦ بند ١).
  - `pull_request` → `true` لو أي «ملف اتلمس» جوه §٧-٢، وغير كده `false`.
  - `git diff` فشل أو الـ range مش موجود أو القايمة طلعت فاضية → `true` (fail-open).
  - `--selftest`: حالات ثابتة + اختبار على ريبو git مؤقت (§٧-٤) بيتشغّلوا في CI على كل PR.
- job جديد `storefront-isr-integration-changes` («detect changes»): checkout بـ `fetch-depth: 0` ← الـ selftest ← السكربت على فرق الـ PR ← `run`. الـ job ده بيشتغل على كل PR.
- job الـ integration: `needs` + `if: run == 'true'` بس. المجموعات والخطوات والأوامر زي ما هي بالحرف. لما `run=false` الـ job بيظهر skipped.
- `docs/maps/code-map.md` (سطر `ci.yml` والسكربت الجديد) · العقد ده (الحالة + السجل).

### ٧-٤ القبول
- الـ selftest بينجح بحالات منها على الأقل: وثائق بس → `false` · `apps/admin` بس → `false` · `backend/db` بس → `false` · ملف في `apps/storefront` → `true` · `packages/core` → `true` · `pnpm-lock.yaml` → `true` · `package.json` في الجذر → `true` · `ci.yml` → `true` · وثائق + ملف متجر → `true` · push → `true` · `workflow_dispatch` → `true` · قايمة فاضية أو مش مقرية → `true`. سطر النتيجة في اللوج، وأي حالة فاشلة = CI فاشل.
- **حالات الحذف والنقل في الـ selftest الثابت (على قايمة المسارات):** حذف ملف جوه النطاق → `true` · طرفي نقل من جوه لبرّه (`apps/storefront/scripts/isr-integration/source.mjs` و`scripts/isr-source.mjs`) → `true` · طرفي نقل من برّه لجوه → `true` · طرفي نقل من برّه لبرّه (مثلًا `docs/a.md` و`docs/b.md`) → `false`.
- **إثبات إن طريقة جمع الفرق مابتوقعش الحالات دي (selftest على ريبو git مؤقت بيتعمل وقت الاختبار، مش الريبو الحقيقي):** commit أساسي فيه ملف جوه النطاق وملف برّه، وبعدين commit لكل حالة، والسكربت بيجمع الفرق **بنفس الدالة اللي بيستخدمها على الـ PR**:
  - (أ) حذف الملف اللي جوه النطاق → القايمة فيها المسار المحذوف، و`run=true`.
  - (ب) `git mv` من جوه النطاق لبرّه (المحتوى زي ما هو) → القايمة فيها المسارين القديم والجديد، و`run=true`.
  - (ج) `git mv` من برّه لجوه → المسارين، و`run=true`.
  - (د) تعديل الملف اللي برّه بس → `run=false`.
  - **ضابط إن الحالة (ب) حقيقية — تلات إثباتات منفصلة على نفس الـ diff بتاع (ب) في الريبو المؤقت:**
    1. `git diff -M --name-status`: لازم يطلّع سطر إعادة تسمية `R<score>` (مثلًا `R100`) فيه **المسار القديم والمسار الجديد**. لو Git ماكشفش إعادة التسمية (مفيش سطر `R` بالمسارين دول)، الضابط بيفشل صراحة ومابيعدّيش.
    2. `git diff -M --name-only`: لازم تطلع قايمة الأسماء فيها **المسار الجديد ومن غير المسار القديم** — يعني الجمع الافتراضي مع كشف إعادة التسمية كان هيوقع المسار القديم (الثغرة اللي في §٧-١).
    3. دالة الجمع الفعلية (`git -c core.quotepath=false diff --no-renames --name-only -z`): لازم ترجّع **المسارين القديم والجديد**، والقرار `run=true`.
- على PR التنفيذ نفسه (بيلمس `ci.yml`): الـ detect بيطلّع `true` مع الملفات اللي طابقت، والمجموعات التلاتة بتشتغل كاملة وبتنجح.
- مسار التخطّي مثبت بالـ selftest. التأكيد العملي (job skipped) على أول PR وثائق بعد الدمج، كملاحظة مش شرط للدمج.
